**기능 폴더**: `specs/002-view-orders` | **작성일**: 2026-10-11 | **입력**: [spec.md](spec.md), [plan.md](plan.md)

- "사용자 결정 (2026-10-11)"이라고 적은 것은 사용자가 정한 것이다. 1절에 모았다.

- 이 문서는 항목 ID를 되도록 쓰지 않고 이름으로 부른다. ID를 쓴 곳에는 바로 아래에 출처와 원문을 펼쳤다.

## 2. plan이 정할 것에 대한 선택지

### 항목 1. 403, 404, 400 응답 본문의 오류 종류(`code`) 값

- **문제**: 테스트 케이스 문서의 공통 전제는 오류 응답 코드(401, 403, 404)와 "토큰이 없으면 `code`는 `UNAUTHORIZED`"만 정했다. 403과 404의 `code` 값은 정하지 않았다. 관리자 조회가 없는 상태 이름을 400으로 거부하는 경우(시나리오 4.3)도 `code` 값이 필요하다. spec은 이 400을 "plan이 정할 것"에 적지 않았지만, 같은 문제라서 함께 정한다.
- **고른 안 `[제안]`**:

  | 상황 | HTTP 상태 | `code` | `type` |
  |---|---|---|---|
  | 관리자가 아닌 사람의 관리자 조회 | 403 | `FORBIDDEN` | `urn:msa-example:problem:FORBIDDEN` |
  | 다른 고객의 주문, 없는 주문, 숫자가 아닌 주문 번호 | 404 | `ORDER_NOT_FOUND` | `urn:msa-example:problem:ORDER_NOT_FOUND` |
  | 잘못된 조회 조건(상태 이름, 해제 결과 값, 쪽 번호, 쪽 크기) | 400 | `INVALID_QUERY_PARAMETER` | `urn:msa-example:problem:INVALID_QUERY_PARAMETER` |

  - 400 본문은 001이 정한 `errors`(필드별 오류 `field`, `message`)에 틀린 매개변수 이름을 담는다.
  - 404는 한 가지 `code`와 한 가지 `detail` 글만 쓴다. 다른 고객의 주문과 없는 주문의 응답이 달라지면 그 주문이 있는지 알 수 있기 때문이다.
- **STD-010 확인**: 001의 계약 파일(`specs/001-place-order/contracts/order-api.yaml`)에서 `Problem.code`는 `type: string`이고 값 목록(`enum`)이 아니다. 그 파일 설명이 "티켓 002에서 조회 오류 값을 더할 수 있도록 enum으로 묶지 않는다. 모르는 값은 status로 판단한다"고 적었다. 값 3개를 더해도 기존 필드를 지우거나, 이름·타입·뜻을 바꾸거나, 상태 값(enum)을 더하는 것이 아니다. 그래서 규칙을 어기지 않는다. 새로 만드는 조회 API의 응답이라서 기존 응답은 하나도 바뀌지 않는다.

> **STD-010** · `docs/standards/architecture-rules.md` 2절 "서비스 사이 호출"
> 규칙: API와 이벤트는 추가하는 방식으로만 바꾼다. 필드를 지우거나 이름·타입·뜻을 바꾸지 않는다. 깨는 변경이 꼭 필요하면 ADR을 먼저 쓴다. 받는 쪽은 모르는 필드를 무시한다. 상태 값(enum)을 추가하는 것은 깨는 변경으로 본다. 이 규칙은 main에 병합된 `contracts/` 현재본을 기준으로 한다. 병합하기 전의 PR 안에서 계약을 고치는 것은 깨는 변경이 아니다
> 이유: 배포 중에는 옛 버전과 새 버전이 서로 호출한다

- **이유**: 001의 값 이름(`UNAUTHORIZED`, `INVALID_ORDER_ITEMS`)처럼 대문자 스네이크 케이스로 쓰고, 무엇이 문제인지 이름에 담았다.
- **고려한 대안**:
  - 404를 `NOT_FOUND`로 쓴다. 없는 경로에 Spring이 내는 404와 구별되지 않는다. 고르지 않았다.
  - 400의 `code`를 매개변수마다 나눈다(`INVALID_STATUS` 등). 값이 늘고 얻는 것이 없다. 고르지 않았다.
- **기대값 출처**: 이 `code` 값은 Claude가 정했다. 2026-10-12에 사용자가 승인해 테스트 케이스 문서의 공통 전제에 더해졌다(PR #30). 이제 인수 시나리오 테스트가 `code` 값을 검사할 수 있다.

### 항목 2. 조회 성공 응답 코드

- **문제**: 테스트 케이스 문서의 공통 전제에는 주문 생성의 성공 코드(201, 200)만 있다.
- **고른 안 `[제안]`**: 001 research.md 결정 13의 표에 아래 행을 이어 쓴다.

  | API | 상황 | 상태 코드 |
  |---|---|---|
  | `GET /orders` | 자기 주문 목록. 주문이 없어 빈 목록이어도 같다 | 200 |
  | `GET /orders/{orderNo}` | 자기 주문 하나 | 200 |
  | `GET /orders/{orderNo}` | 다른 고객의 주문, 없는 주문, 숫자가 아닌 주문 번호 | 404 |
  | `GET /admin/orders` | 조건에 맞는 모든 주문. 조건 없음과 결과 없음 포함 | 200 |
  | `GET /admin/orders` | 없는 상태 이름, 없는 해제 결과 값, 잘못된 쪽 번호·크기 | 400 |
  | 조회 API 세 개 | 토큰이 없거나 검증 실패 | 401 |
  | `GET /admin/orders` | 관리자가 아님 | 403 |

- **이유**: 읽기는 새 자원을 만들지 않아서 201이 아니다. 빈 목록은 오류가 아니라서(시나리오 2.3 "오류 없이 빈 목록을 받는다") 본문이 있는 200이다.
- **고려한 대안**: 빈 목록에 204를 쓰면 호출하는 쪽이 본문 없는 응답을 따로 처리해야 한다. 빈 목록에 404를 쓰면 시나리오 2.3과 어긋난다. 둘 다 고르지 않았다.
- **기대값 출처**: 200은 2026-10-12에 사용자가 승인해 테스트 케이스 문서의 공통 전제에 더해졌다(PR #30).

### 항목 3. 목록의 정렬과 페이지 크기

- **문제**: 유스케이스 문서가 목록의 정렬과 페이지 크기를 plan에서 정한다고 적었다. 페이징은 코딩 규약 3-2절 "MyBatis와 SQL"의 `OFFSET ... ROWS FETCH NEXT ... ROWS ONLY`를 따른다. 페이지 크기에는 수치 목표를 만들지 않는다.
- **고른 안 `[제안]`**:
  - **정렬**: 주문 번호가 큰 순서(`ORDER BY ORDER_NO DESC`)다. 최근 주문이 먼저 나온다. 주문 안의 항목은 001처럼 상품 ID 순이다.
  - **쪽 지정**: 쿼리 매개변수 `page`(0부터, 기본 0)와 `size`(기본 20, 최대 100)다. 목록 API 두 개(`GET /orders`, `GET /admin/orders`)가 같은 규칙을 쓴다.
  - **범위 밖 값**: `page`가 0보다 작거나, `size`가 1보다 작거나 100보다 크거나, 정수가 아니면 400(`INVALID_QUERY_PARAMETER`)이다. 값을 조용히 바꾸지 않는다.
  - **응답 모양**: 배열 하나가 아니라 `{ "orders": [...], "page": 0, "size": 20, "hasNext": false }` 객체다. `hasNext`는 다음 쪽이 있는지 알린다. SQL이 `size + 1`개를 읽어서 정한다. 전체 개수를 세는 쿼리(`COUNT`)는 만들지 않는다.
  - **SQL 모양**: 주문과 항목은 1:N이다. 두 표를 먼저 합친 뒤 행 개수로 자르면 주문 하나가 쪽 사이에서 잘린다. 그래서 `ORDERS`에서 주문을 먼저 정렬하고 자른 결과(인라인 뷰)에 `ORDER_ITEMS`를 합친다. 이 SQL이 실제 Oracle에서 맞게 도는지는 Mapper 테스트로 확인한다(4절).
- **이유**:
  - 주문 번호는 시퀀스에서 나와 시간 순서와 같이 커지고, 값이 겹치지 않는다. 정렬이 안정적이고 기본 키 인덱스를 쓴다.
  - 20과 100은 응답 한 번의 크기를 정하는 값이다. 응답 시간이나 처리량의 목표값이 아니다. `docs/requirements/non-functional.md`의 표에는 조회에 해당하는 행이 없다. 그래서 수치 목표를 만들지 않았다.
  - 20과 100은 도메인 클래스의 상수로 둔다. 설정값 규칙(코딩 규약 3-5절)은 제한 시간, 재시도, 다른 서비스 주소, 비밀번호를 대상으로 한다. 환경마다 다른 값이 아니라서 `@ConfigurationProperties`를 더하지 않는다.
  - 배열 하나로 응답하면 나중에 `hasNext` 같은 필드를 더할 수 없다. 배열을 객체로 바꾸는 것은 깨는 변경이기 때문이다. 처음부터 객체로 쓴다.
- **고려한 대안**:
  - `created_at` 순서(`CREATED_AT DESC`). 시각이 같은 주문이 있으면 순서가 정해지지 않아서 주문 번호를 보조 기준으로 또 붙여야 한다. 주문 번호만 쓰는 쪽이 더 단순하다.
  - 오래된 주문부터(`ORDER_NO ASC`). 고객은 최근 주문을 먼저 찾는다. 고르지 않았다.
  - 마지막으로 읽은 주문 번호를 넘기는 커서 방식(keyset paging). 코딩 규약이 `OFFSET`을 정했다. 이 프로젝트에는 많은 주문을 읽는 목표가 없다. 고르지 않았다.
  - `COUNT`로 전체 개수를 돌려준다. 쿼리가 하나 더 늘고, 요청받은 필드가 아니다. 고르지 않았다.
- **알아 둘 것**: `OFFSET` 방식은 쪽을 넘기는 사이에 새 주문이 생기면 같은 주문이 다음 쪽에 한 번 더 나올 수 있다. 최근 주문이 먼저 오는 정렬이라서 새 주문이 앞쪽에 끼어들기 때문이다. 이 프로젝트의 규모에서는 받아들인다.
- **기대값 출처**: 정렬 순서, 20과 100, `hasNext`, 범위 밖 400은 2026-10-12에 사용자가 승인해 테스트 케이스 문서의 공통 전제와 새 테스트 케이스에 더해졌다(PR #30). spec의 시나리오 2.6이 이 케이스를 가리킨다. 받치는 테스트의 기대값도 이 문서에서 가져온다.

### 항목 4. 관리자 조회에서 해제 결과가 빈 주문을 찾는 조건

- **문제**: "실패" 주문 가운데 해제를 하던 인스턴스가 사라져 해제 결과가 비어 있는 주문을 관리자가 찾아야 한다. 시나리오 4.4는 상태 "실패"로 조회해서 세 주문을 받고, 그 가운데 해제 결과가 비어 있는 주문이 비어 있는 채로 나오는 것을 확인한다.
- **고른 안 `[제안]`**: 해제 결과가 빈 주문만 거르는 조건을 새로 만들지 않는다. 관리자는 `status=FAILED`로 조회하고, 응답에서 `releaseStatus`가 `null`인 주문을 읽는다.
- **이유**:
  - 해제 결과가 비는 경우는 "실패" 주문만이 아니다. "처리중" 주문도 해제 결과가 비어 있다(001 data-model.md 4-2절). 그래서 "빈 것"을 따로 거르는 조건은 상태 조건과 함께 써야 의미가 있다.
  - 시나리오 4.4가 확인하는 방법이 이것이다. 테스트 케이스 문서에 "비어 있음" 조건의 기대값이 없다. 요청받지 않은 조건을 더하지 않는다.
- **고려한 대안**:
  - 쿼리 값에 `releaseStatus=NONE`을 허용한다. 저장되는 값 목록에 없는 값이 요청에만 생긴다. 응답의 해제 결과 값과 헷갈린다.
  - 불리언 매개변수 `releaseStatusEmpty=true`를 더한다. 매개변수가 하나 늘고 문서에 기대값이 없다.
  - 두 대안은 나중에 필요해지면 추가로 더할 수 있다. 쿼리 매개변수를 더하는 것은 기존 호출을 깨지 않는다.
- **한계**: 실패한 주문이 많으면 관리자가 쪽을 넘기며 `releaseStatus`가 `null`인 줄을 찾아야 한다. 이 한계는 받아들인다.

### 항목 5. 경로, 필드, 쿼리 매개변수 이름

- **기준**: `docs/design/architecture.md` 5절 "인터페이스 (개념 수준)" 표의 외부 행이다. 그 표는 경로와 쿼리 매개변수를 이렇게 적었다.

  | 메서드와 경로 | 입력 | 출력 |
  |---|---|---|
  | `GET /orders` | JWT | 자기 주문 목록 |
  | `GET /orders/{orderNo}` | JWT | 자기 주문 하나. 남의 주문이면 404 |
  | `GET /admin/orders?status=&releaseStatus=` | JWT(`ADMIN`) | 조건에 맞는 모든 주문 |

- **고른 안 `[제안]`**: 경로 세 개와 쿼리 매개변수 `status`, `releaseStatus`는 표 그대로다. 표에서 달라진 것은 없다. 표에 없는 것을 아래처럼 더했다.
  - 목록 두 개에 `page`, `size`를 더했다(항목 3).
  - 응답 필드 이름은 001의 `OrderResponse`를 이어 쓴다: `orderNo`, `status`, `reason`, `shortageProductIds`, `missingProductIds`. 새 필드는 `items`(각 줄 `productId`, `quantity`)와 `createdAt`(주문 시각)이다. `items`는 001 주문 요청의 이름과 같다. 관리자 응답에는 `releaseStatus`를 더한다(항목 6).
  - 쿼리 매개변수 값은 001 응답에 쓴 이름 문자열 그대로다. `status`는 `PENDING`, `CONFIRMED`, `REJECTED`, `FAILED`이고 `releaseStatus`는 `NOT_REQUIRED`, `RELEASED`, `RELEASE_FAILED`다. 대소문자를 구분한다. 빈 값(`status=`)도 없는 이름이라서 400이다.
- **이유**: 한 서비스의 같은 개념에 이름을 둘 쓰지 않는다. 고객이 주문 생성 응답에서 본 `status` 값과 조회 응답의 `status` 값이 같아야 한다.
- **사용자가 확인할 것**: 위에서 "더한 것"이 "표와 다르게 정하는 것"에 드는지 판단은 사용자 몫이다. Claude는 표에 없는 요소를 더한 것으로 보고 보고서에 따로 적는다.

### 항목 6. 관리자 응답의 해제 결과 표현

- **문제**: 001 research.md 결정 13의 `[제안]`은 일반 주문 응답에 `releaseStatus`를 넣지 않는다고 했다. 관리자 조회에는 해제 결과가 나와야 한다(BR-102).

> **BR-102** · `docs/requirements/uc-002-view-orders.md` 3절 "업무 규칙"
> 관리자 조회에는 재고 해제 결과(해제 완료/해제 실패)가 함께 나온다

- **고른 안 `[제안]`**: 관리자 조회만 응답 DTO를 따로 둔다(`AdminOrderResponse`). 고객용 응답(`OrderDetailResponse`)의 모든 필드에 `releaseStatus` 한 필드를 더한 모양이다.
  - 값은 `NOT_REQUIRED`, `RELEASED`, `RELEASE_FAILED` 또는 `null`이다. 값이 비어 있는 주문은 필드를 빼지 않고 `"releaseStatus": null`로 낸다. 시나리오 4.4가 "비어 있는 채로 나온다"고 확인한다.
  - 고객용 응답과 주문 생성 응답에는 `releaseStatus`를 넣지 않는다. 001의 `[제안]`과 같다.
- **STD-010 확인**: 새 응답 스키마를 새 API에 쓴다. 이미 있는 응답(`POST /orders`)은 바뀌지 않는다. 필드를 지우거나 이름·타입·뜻을 바꾸는 것이 없다. 위반이 아니다. 나중에 고객용 응답에 `releaseStatus`를 더하게 되어도 필드를 더하는 일이라서 STD-010이 허용한다.

> **STD-010** · `docs/standards/architecture-rules.md` 2절 "서비스 사이 호출"
> 규칙: API와 이벤트는 추가하는 방식으로만 바꾼다. 필드를 지우거나 이름·타입·뜻을 바꾸지 않는다. 깨는 변경이 꼭 필요하면 ADR을 먼저 쓴다. 받는 쪽은 모르는 필드를 무시한다. 상태 값(enum)을 추가하는 것은 깨는 변경으로 본다. 이 규칙은 main에 병합된 `contracts/` 현재본을 기준으로 한다. 병합하기 전의 PR 안에서 계약을 고치는 것은 깨는 변경이 아니다
> 이유: 배포 중에는 옛 버전과 새 버전이 서로 호출한다

- **이유**: 고객에게 재고 해제 상태를 보여 줄 이유가 유스케이스 문서에 없다. 요청받지 않은 정보는 내보내지 않는다.
- **고려한 대안**: 응답 DTO 하나로 합치고 고객에게는 `null`을 낸다. 고객에게 내부 상태 필드가 보이고, `null`이 "값이 없음"인지 "숨김"인지 구별되지 않는다. 고르지 않았다.
- **사용자가 확인할 것**: 관리자 응답에 주문한 고객의 ID(`customerId`)를 넣지 않았다. 유스케이스 문서와 테스트 케이스에 요구가 없다. 시나리오 4.2는 "C1과 C2의 실패 주문"을 주문 번호로 확인할 수 있다. 관리자가 주문의 주인을 알아야 하면 `customerId`를 더해야 한다. 필드를 더하는 것은 아키텍처 규칙 2절의 "추가하는 방식으로만 바꾼다" 규칙이 허용한다. 지금은 더하지 않았다.

### 항목 8. 계약 파일의 위치

- **상태**: 사용자 결정 (2026-10-11). 조회 API의 OpenAPI는 `specs/002-view-orders/contracts/order-query-api.yaml`에 쓴다. 저장소 루트 `contracts/`의 현재본은 고치지 않는다.
- **헌법 II절 "계약 우선"의 "plan에서 확인할 질문"에 대한 답**:
  - *이 기능이 서비스 사이 API나 이벤트를 바꾸는가?* 바꾸지 않는다. 이 기능이 더하는 API 세 개는 고객과 관리자가 부르는 외부 API다. `docs/design/architecture.md` 5절 표가 이 셋을 "외부" 구분으로 적었다. 서비스 사이(내부) API인 재고 예약·해제는 바뀌지 않는다. 그래서 루트 `contracts/`의 현재본을 고치지 않는다.
  - *지우는 필드, 이름·타입·뜻이 바뀌는 필드, 새로 더하는 상태 값이 있는가?* 없다. 모두 새 API의 새 스키마다. 오류 `code` 값 3개를 더하지만 `code`는 값 목록(`enum`)이 아니다(항목 1).
- **근거**: 서비스 사이 API와 이벤트를 바꾸면 같은 PR에서 `contracts/`도 고치라는 규칙(STD-014)이 이 기능에는 닿지 않는다.

> **STD-014** · `docs/standards/architecture-rules.md` 2절 "서비스 사이 호출"
> 규칙: 서비스 사이 API와 이벤트를 바꾸면 같은 PR에서 `contracts/`의 현재본(OpenAPI, AsyncAPI)도 고친다
> 이유: `specs/NNN/contracts/`에는 그 기능에서 바뀐 부분만 있어 전체 계약을 알 수 없다

- **알아 둘 것 1**: 루트 `contracts/`에는 외부 API인 `POST /orders`의 계약도 없다. 001은 그 계약을 `specs/001-place-order/contracts/order-api.yaml`에만 두었다(그 파일 설명: "이 파일은 서비스 사이 API가 아니라서 저장소 루트 contracts/에 두지 않는다"). 기준 문서에는 외부 API의 현재 전체 명세를 둘 위치가 없다. 그래서 `specs/002-view-orders/contracts/order-query-api.yaml`도 "이 기능이 더한 부분"만 담는다. 외부 API 전체를 한곳에서 보려면 위치를 정하는 문서 PR이 따로 필요하다. 이 plan에서 정하지 않았다.
- **알아 둘 것 2**: 001의 계약 파일은 이 티켓에서 고치지 않는다(`specs/001-place-order/`는 고치지 않는 산출물). 조회 계약 파일은 `Problem`과 `FieldError` 스키마를 자기 파일에 다시 적는다. 두 파일의 `Problem`이 어긋나지 않게 하는 일은 사람이 맡는다. 두 파일을 하나로 합치는 일도 위치를 정하는 문서 PR과 함께 다룬다.
- **계약 검증**: 서비스 사이 API의 계약 테스트 층(제공자·소비자)은 이 파일을 검증하지 않는다. 001도 `order-api.yaml`을 검증하는 테스트를 만들지 않았다. 이 plan도 만들지 않는다. 응답 필드는 인수 시나리오 테스트가 필드 이름까지 직접 검사한다. 이 선택은 5절에서 다시 다룬다.

### 항목 9. 보안 설정

- **문제**: (a) 403(`ADMIN`이 아닌 사람)과 401을 Problem Details로 내는 방법, (b) `ADMIN` 역할을 토큰에서 읽는 방법, (c) 고객 ID를 토큰에서 꺼내는 기존 방법의 재사용.
- **지금 코드에서 읽은 것**:
  - `SecurityConfig`는 health를 열고 나머지 요청을 모두 `authenticated()`로 막는다. 역할로 막는 규칙이 없다. JWT는 `Customizer.withDefaults()`로 검증한다.
  - `ProblemAuthenticationEntryPoint`가 401을 Problem Details(`code = UNAUTHORIZED`)로 낸다. `accessDeniedHandler`는 없다. 없으면 Spring Security의 기본 처리기가 403을 내고, 이 프로젝트가 정한 `code` 필드를 담지 않는다. 기본 처리기의 응답 본문 모양은 확인하지 못했다(4절).
  - `OrderController.place`는 `@AuthenticationPrincipal Jwt jwt`에서 `jwt.getSubject()`로 고객 ID를 얻는다.
- **고른 안 `[제안]`**:
  1. **401**: 바꾸지 않는다. 조회 API 세 개도 `anyRequest().authenticated()`에 걸리고, 기존 `ProblemAuthenticationEntryPoint`가 같은 본문으로 낸다.
  2. **403**: `ProblemAccessDeniedHandler`를 `exception` 패키지에 새로 만든다. `ProblemAuthenticationEntryPoint`와 같은 방식으로 403 Problem Details(`code = FORBIDDEN`)를 쓴다. `SecurityConfig`의 `exceptionHandling`에 등록한다.
  3. **관리자 규칙**: `/admin/**` 경로를 `hasRole("ADMIN")`으로 막는다. `GET /admin/orders` 하나만이 아니라 `/admin/` 아래 전체를 막는다. 나중에 관리자 경로가 늘어도 권한 없이 열리는 일이 없게 하려는 것이다. 토큰이 없으면 규칙이 403이 아니라 401을 먼저 낸다(인증 실패가 먼저다).
  4. **역할 읽기**: `JwtAuthenticationConverter`를 새로 설정한다. 토큰의 `realm_access.roles` 목록의 이름마다 `ROLE_` 접두어를 붙여 Spring Security 권한으로 바꾼다(`ADMIN` → `ROLE_ADMIN`). Spring Security의 기본 변환기는 `scope` 값만 읽어서 Keycloak의 realm 역할을 권한으로 바꾸지 못한다.
  5. **고객 조회의 권한**: `GET /orders`, `GET /orders/{orderNo}`는 로그인만 요구하고 역할은 요구하지 않는다. 시나리오 2.5가 관리자 역할만 있는 사용자도 이 조회를 쓴다고 정했다. 주문 생성의 기존 규칙(역할과 관계없이 로그인한 사용자)과 같다.
  6. **고객 ID**: 기존과 같이 `@AuthenticationPrincipal Jwt jwt`의 `jwt.getSubject()`로만 얻는다. 쿼리 매개변수나 헤더로 받은 고객 ID는 쓰지 않는다(STD-017).

> **STD-017** · `docs/standards/architecture-rules.md` 5절 "보안"
> 규칙: 외부에 열린 API는 Keycloak이 발급한 JWT를 서비스가 직접 검증한다(OAuth2 Resource Server). 사용자 식별은 토큰의 `sub`로 하고, 요청 본문이나 별도 헤더로 받은 사용자 ID를 믿지 않는다
> 이유: Gateway를 거치지 않은 요청도 막고, 사용자 위조를 막는다

  `ADMIN`과 `CUSTOMER` 역할이 사용자에게 붙는 방식은 ADR-0006이 정했다. 이 plan은 그 결정을 바꾸지 않는다.

> **ADR-0006** · `docs/adr/0006-keycloak-jwt-auth.md` 제목, "결정" 절
> 제목: ADR-0006 인증은 Keycloak이 발급한 JWT를 각 서비스가 검증한다
> 결정:
> - **토큰 발급**: Keycloak을 OIDC 제공자로 쓴다. realm 하나에 고객(`CUSTOMER`)과 관리자(`ADMIN`) 계정을 초기 데이터로 넣는다. 회원 가입 기능은 만들지 않는다.
> - **토큰 검증**: 주문 서비스가 Spring Security OAuth2 Resource Server로 JWT를 직접 검증한다. Gateway는 `Authorization` 헤더를 그대로 넘긴다.
> - **사용자 식별**: 토큰의 `sub`를 고객 ID로 쓴다.
> - **서비스 간 호출**: 재고 서비스는 외부에 열지 않으므로 이번 단계에서는 인증하지 않는다.
> - **테스트**: 서비스 통합 테스트는 Spring Security Test의 JWT 지원으로 사용자를 흉내 낸다. E2E는 테스트 전용 Keycloak 클라이언트에서 사용자 이름과 비밀번호로 토큰을 받는다. 이 방식은 테스트 전용 클라이언트에만 켠다.

- **이유**: 서비스가 JWT를 직접 검증하는 구조(위 두 인용)는 그대로다. 바뀌는 곳은 "토큰의 역할을 권한으로 바꾸는 한 곳"과 "403을 본문 있는 응답으로 내는 한 곳"이다. `docs/design/architecture.md` 7절이 "역할은 Keycloak realm 역할(`CUSTOMER`, `ADMIN`)을 Spring Security 권한으로 바꿔 쓴다"고 이미 적었다.
- **고려한 대안**:
  - 컨트롤러 메서드에 `@PreAuthorize("hasRole('ADMIN')")`를 붙인다. 메서드 보안을 켜는 설정이 더 필요하다. 경로 규칙 한 줄로 충분하다.
  - 컨트롤러 안에서 `jwt.getClaim("realm_access")`를 직접 읽어 403을 던진다. 컨트롤러가 권한 판단을 하게 된다. 코딩 규약 3-1절은 컨트롤러가 업무 판단을 하지 않는다고 정했다.
- **테스트 때 알아 둘 것**: Spring Security Test의 `jwt()`는 이 plan이 만드는 변환기를 거치지 않는다. 권한은 `jwt().authorities(...)`로 직접 준다. 그래서 변환기가 `realm_access.roles`를 읽는지는 인수 시나리오 테스트가 아니라 변환기의 단위 테스트(받치는 테스트)로 확인한다. 진짜 Keycloak 토큰으로 `ADMIN`이 통과하는지는 티켓 003의 E2E에서 확인한다. 4절에 적었다.

### 항목 10. DB: 새 마이그레이션이나 인덱스가 필요한가

- **고른 안 `[제안]`**: 새 Flyway 파일을 만들지 않는다. 인덱스도 더하지 않는다.
- **이유**:
  - 조회에 필요한 열이 모두 `ORDERS`와 `ORDER_ITEMS`에 이미 있다: `ORDER_NO`, `CUSTOMER_ID`, `STATUS`, `REASON`, `RELEASE_STATUS`, `CREATED_AT`, `PRODUCT_ID`, `QUANTITY`, `REJECT_REASON`. 확인: `V1__orders.sql`을 읽었다.
  - 값 목록을 막는 CHECK 제약이 있어서 쿼리 값 검사(`status`, `releaseStatus`)와 어긋나지 않는다.
  - 고객 목록과 주문 하나 조회는 기존 인덱스를 쓴다. `UK_ORDERS_CUSTOMER_KEY`는 `(CUSTOMER_ID, REQUEST_KEY)`로 `CUSTOMER_ID`가 맨 앞이라 고객 조건을 받친다. 주문 번호 조건은 기본 키(`PK_ORDERS`)가 받친다.
  - 관리자의 `STATUS`, `RELEASE_STATUS` 조건에는 인덱스가 없다. 조회의 응답 시간 목표가 없고(항목 3의 근거), 이 프로젝트의 주문 수는 적다. 인덱스는 필요한 때 새 Flyway 파일로 더한다(코딩 규약 3-3절: 적용된 파일은 고치지 않고 새 파일을 더한다).
- **한계**: 실행 계획은 확인하지 못했다(4절). 위 설명은 `V1__orders.sql`의 제약 정의를 읽고 쓴 것이다.
- **고려한 대안**: `(STATUS, ORDER_NO)` 인덱스를 지금 더한다. 요청받지 않았고 목표값도 없다. 고르지 않았다.

### 항목 11. 다른 고객의 주문을 "없음"과 같은 응답으로 만드는 방법

- **고른 안 `[제안]`**: 조회 조건에 고객을 넣는다. 주문 하나 조회의 SQL은 `WHERE ORDER_NO = #{orderNo} AND CUSTOMER_ID = #{customerId}` 하나다. 고객 ID는 토큰의 `sub`다. 다른 고객의 주문은 조건에 맞는 줄이 없어서 없는 주문과 똑같이 빈 결과가 된다. 서비스는 빈 결과를 `ORDER_NOT_FOUND`(404)로 바꾼다.
- **주문 번호가 숫자가 아닌 경우**: 컨트롤러가 `{orderNo}`를 숫자 타입이 아니라 글자로 받는다. 숫자 타입으로 받으면 `abc`에 Spring이 400을 낸다. 시나리오 1.3은 404를 요구한다. 글자를 도메인의 `OrderNumbers.parse`가 숫자로 바꾸고, 숫자가 아니거나 `long`에 담기지 않으면 DB를 부르지 않고 같은 404를 낸다.
- **같은 응답의 뜻**: 세 경우(다른 고객의 주문, 없는 주문, 숫자가 아닌 주문 번호)에 상태 코드, `type`, `title`, `detail`, `code`가 모두 같다. `detail` 글에는 요청한 주문 번호를 담지 않는다. 담으면 경우마다 글이 달라진다. 이것이 "그 주문이 있는지도 알 수 없게 한다"(BR-101)를 지키는 방법이다.

> **BR-101** · `docs/requirements/uc-002-view-orders.md` 3절 "업무 규칙"
> 고객은 다른 고객의 주문을 볼 수 없다. 다른 고객의 주문 번호로 조회하면 "없음"으로 응답해, 그 주문이 있는지도 알 수 없게 한다

- **이유**: 고객 조건이 SQL에 있으면 "남의 주문"이라는 분기 자체가 코드에 없다. 코드가 남의 주문을 읽은 뒤 거르는 구조에서는 거르는 코드를 잘못 쓰는 순간 남의 주문이 나간다. SQL 조건 한 줄이 더 안전하다.
- **고려한 대안**: 주문 번호로 먼저 읽고 서비스에서 주인을 비교해 404를 낸다. 같은 응답을 내는 코드 경로가 둘이 되고, 비교를 빼먹으면 남의 주문이 나간다. 고르지 않았다.

### 항목 15. 주문 시각(`createdAt`)의 표현 (plan을 쓰며 생긴 것)

- **문제**: 시나리오 1.5가 "주문 시각이 나온다"고 확인한다. 어떤 형식으로 내는지 문서에 없다. `ORDERS.CREATED_AT`은 `TIMESTAMP`(시각대 정보 없음)이고, `insertOrder`가 `SYSTIMESTAMP`(DB 서버의 시각대를 가진 시각)로 넣는다.
- **고른 안 `[제안]`**: 필드 이름은 `createdAt`이다. MyBatis가 `java.time.LocalDateTime`으로 읽고, JSON에는 시각대 없는 ISO 8601 글자(예: `2026-10-11T13:45:11.123456`)로 낸다. 계약 파일의 설명에 "DB 서버 시각대 기준"이라고 적는다.
- **이유**: 저장된 값을 바꾸지 않고 그대로 낸다. 코드가 시각대를 추측해서 바꾸지 않는다.
- **확인하지 못한 것**: Oracle 컨테이너의 시각대가 UTC인지, `LocalDateTime`으로 읽은 값이 `SYSTIMESTAMP`로 넣은 값과 같은지 실행해서 확인하지 못했다(4절). JSON 직렬화가 위의 글자 모양으로 나오는지도 확인하지 못했다.
- **고려한 대안**: UTC 시각(`Instant`)으로 낸다. DB 서버의 시각대를 알아야 안전하게 바꿀 수 있고, 지금은 모른다. 시각대를 못 박으려면 기록하는 SQL(`insertOrder`)을 바꿔야 한다. 이미 있는 SQL을 고치는 일이라서 이 plan에서 고르지 않았다.
- **사용자가 정할 것**: 시각대가 없는 글자로 시작해도 되는지, 아니면 UTC로 못 박는 변경을 이 티켓에 넣을지.

## 용어

- **쪽 지정 (paging)**: 많은 결과를 정해진 개수씩 나눠 읽는 것이다. 이 기능은 `page`(몇 번째 쪽, 0부터)와 `size`(한 쪽의 개수)로 지정한다.
- **오프셋 방식 (offset paging)**: 앞에서 몇 줄을 건너뛰고 몇 줄을 읽을지 정하는 쪽 지정 방식이다. SQL에서는 `OFFSET ... ROWS FETCH NEXT ... ROWS ONLY`로 쓴다.
- **커서 방식 (keyset paging)**: 마지막으로 읽은 줄의 값을 넘겨 "그다음부터"를 읽는 쪽 지정 방식이다. 이 기능은 쓰지 않는다.
- **인라인 뷰 (inline view)**: SQL의 `FROM` 자리에 쓰는 안쪽 SELECT다. 이 기능은 주문을 먼저 정렬하고 자른 결과에 주문 항목을 합치는 데 쓴다.
- **응답 봉투 (response envelope)**: 목록 자체가 아니라, 목록과 쪽 정보를 함께 담은 객체로 응답하는 모양이다. 이 기능은 `orders`, `page`, `size`, `hasNext`를 담는다.
- **`hasNext`**: 다음 쪽이 있는지 알리는 응답 필드다. 한 쪽보다 한 줄 더 읽어서 정한다.
- **Problem Details (RFC 9457)**: HTTP API의 오류 응답을 JSON으로 적는 표준 형식이다. 이 프로젝트는 모든 오류 응답을 이 형식으로 낸다.
- **`AccessDeniedHandler`**: 로그인은 했지만 권한이 없는 요청을 어떤 응답으로 거부할지 정하는 Spring Security의 처리기다. 이 기능은 403을 Problem Details로 낸다.
- **`JwtAuthenticationConverter`**: 검증한 JWT를 Spring Security의 인증 정보(권한 포함)로 바꾸는 Spring Security의 변환기다. 이 기능은 토큰의 `realm_access.roles`를 권한으로 바꾼다.
- **realm 역할 (realm role)**: Keycloak의 realm 안에서 사용자에게 붙이는 역할이다. 이 프로젝트의 `CUSTOMER`, `ADMIN`이다. 토큰의 `realm_access.roles` 목록에 들어 있다.
- **도우미 클래스 (test support class)**: 여러 테스트가 함께 쓰는 준비 코드를 모아 둔 테스트용 클래스다. 이 기능은 주문 준비 코드를 `ViewTestSupport`에 둔다.
- **받치는 테스트 (supporting test)**: 인수 시나리오를 직접 검증하지 않고 단위, Mapper, 변환기를 확인하는 테스트다. 테스트 케이스 번호를 붙이지 않는다.
- **깨는 변경 (breaking change)**: 옛 버전의 호출하는 쪽이나 받는 쪽이 더는 동작하지 않게 만드는 변경이다. 필드 삭제, 필드 이름 변경, 새 상태 값 추가가 여기에 든다.
- **시각대 (time zone)**: 시각이 어느 지역의 시계 기준인지 나타내는 정보다. 이 기능의 주문 시각(`createdAt`)은 시각대 없이 DB가 저장한 값을 그대로 낸다.
