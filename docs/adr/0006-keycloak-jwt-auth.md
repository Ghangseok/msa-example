# ADR-0006 인증은 Keycloak이 발급한 JWT를 각 서비스가 검증한다

- 상태: 채택
- 날짜: 2026-10-04
- 관련: [UC-001](../requirements/uc-001-place-order.md), [UC-002](../requirements/uc-002-view-orders.md), STD-017, [design 7절](../design/architecture.md#7-인증-adr-0006)

## 배경

OQ-007에서 기본 인증을 넣기로 했다. 주문을 고객과 연결하고, 고객은 자기 주문만 보고, 관리자는 실패한 주문을 찾을 수 있어야 한다. 테스트에서 사용자를 쉽게 바꿔 가며 호출할 수 있어야 한다.

## 결정

- **토큰 발급**: Keycloak을 OIDC 제공자로 쓴다. realm 하나에 고객(`CUSTOMER`)과 관리자(`ADMIN`) 계정을 초기 데이터로 넣는다. 회원 가입 기능은 만들지 않는다.
- **토큰 검증**: 주문 서비스가 Spring Security OAuth2 Resource Server로 JWT를 직접 검증한다. Gateway는 `Authorization` 헤더를 그대로 넘긴다.
- **사용자 식별**: 토큰의 `sub`를 고객 ID로 쓴다. (STD-017)
- **서비스 간 호출**: 재고 서비스는 외부에 열지 않으므로 이번 단계에서는 인증하지 않는다.
- **테스트**: 서비스 통합 테스트는 Spring Security Test의 JWT 지원으로 사용자를 흉내 낸다. E2E는 테스트 전용 Keycloak 클라이언트에서 사용자 이름과 비밀번호로 토큰을 받는다. 이 방식은 테스트 전용 클라이언트에만 켠다. `[제안]`

## 고려한 대안

| 대안 | 고르지 않은 이유 |
|---|---|
| 주문 서비스에 HTTP Basic | 가장 단순하다. 하지만 비밀번호를 서비스가 직접 다루고, 서비스가 늘면 계정이 서비스마다 흩어진다. MSA 인증 구조를 실험할 수 없다 |
| Spring Authorization Server로 인증 서비스를 직접 만듦 | 만들고 관리할 서비스가 하나 늘어난다. 사용자 이름과 비밀번호로 바로 토큰을 받는 방식을 지원하지 않아서 테스트에서 토큰을 얻기 번거롭다 |
| Gateway에서만 JWT 검증 | 서비스 코드가 줄어든다. 하지만 Gateway 구현체에 묶이고, Gateway를 거치지 않은 요청을 서비스가 막지 못한다. 서비스는 사용자 정보를 헤더로 받아야 하므로 위조 방지가 따로 필요하다. 나중에 Envoy Gateway의 SecurityPolicy로 "Gateway와 서비스 모두 검증"으로 넓힐 수 있다 (ADR-0007) |

## 결과

- 좋아지는 점: 서비스 코드는 설정과 권한 규칙만 가진다. 실무에서 흔한 구조(OIDC 제공자 + JWT 리소스 서버)를 그대로 실험한다.
- 감수할 점:
  - Keycloak이 메모리를 0.5~1GB 쓴다.
  - 토큰 발급자(`iss`) 주소가 클러스터 안팎에서 달라지는 문제를 처리해야 한다. (design 7절) `[현장]`
  - 재고 서비스는 클러스터 안에서 누구나 부를 수 있다. 같은 클러스터에 다른 앱이 없는 실습 환경이라 감수한다.

## 바꿀 때

- 결제 서비스가 들어와 서비스 간 호출이 늘면, 서비스 간 인증(토큰 전달 또는 클라이언트 자격 증명, mTLS)을 새 ADR로 정한다.
