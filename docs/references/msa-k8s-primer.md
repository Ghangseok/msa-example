## 0. 예제 시나리오

고객이 상품을 주문한다. 주문 서비스는 재고 서비스에 재고 예약을 요청한다. 예약에 성공하면 주문을 확정하고, 재고가 부족하면 주문을 거절한다.

- 주문 서비스(order)와 재고 서비스(inventory)는 서로 다른 애플리케이션이다.
- 두 서비스는 각각 Pod 2개로 실행되고, 각자 자기 DB를 가진다.

이 문서의 나머지 설명은 모두 이 시나리오를 기준으로 한다.

## 1. 구조가 헷갈리는 이유

쿠버네티스에는 두 종류의 관계가 섞여 있다.

1. **실행 관계**: 무엇이 무엇 위에서 실행되는가
2. **관리 관계**: 무엇이 무엇을 관리하고 가리키는가

이 둘을 한 줄로 이어 붙이면 "서비스 안에 Pod가 있다"처럼 잘못 이해하게 된다. 아래에서 둘을 나눠서 설명한다.

---

## 2. 왜 쪼개는가 — 마이크로서비스의 필요성

온라인 매장을 애플리케이션 하나로 만들었다고 하자. 주문과 재고가 같은 앱, 같은 DB에 있다. 이런 구조를 **모놀리스(monolith, 하나로 된 애플리케이션)** 라고 한다. 주문 코드가 재고를 줄일 때는 메서드 호출 한 번이면 되고, `@Transactional` 하나로 둘을 묶을 수 있다. 단순하고 빠르다.

규모가 커지면 세 가지 문제가 생긴다.

1. **배포**: 재고 화면의 버그 하나를 고쳐도 주문 기능까지 포함한 앱 전체를 다시 배포해야 한다. 배포하는 동안 주문도 영향을 받는다.
2. **확장**: 연말 세일에 주문이 10배 몰려도 재고 조회량은 그만큼 늘지 않을 수 있다. 그래도 앱이 하나라서 통째로 늘려야 한다.
3. **팀**: 주문 팀과 재고 팀이 같은 코드와 같은 DB 테이블을 건드리면 한 팀의 변경이 다른 팀을 깨뜨린다.

**마이크로서비스(microservice)** 는 이 문제를 풀려고 업무 영역별로 앱을 쪼갠다. 쪼갠 앱은 각자 따로 배포되고, 따로 늘어나고, 자기 DB를 따로 가진다.

대가도 있다. 메서드 호출이 네트워크 호출로 바뀌고, DB 트랜잭션 하나로 묶던 것을 더는 묶을 수 없다. 그래서 개발자가 적고 배포·확장 문제가 아직 없는 시스템에는 모놀리스가 더 낫다는 의견이 많다 `[현장]`. 이 예제는 연습용이라 일부러 쪼갠다.

## 3. 쪼갠 앱을 어떻게 실행하는가 — 컨테이너와 쿠버네티스의 필요성

쪼개고 나면 실행할 것이 많아진다. 서비스 2개를 각각 2개씩 띄우면 프로세스가 4개다. 실제 회사에서는 수십 개 서비스가 수백 개로 뜬다. 이것을 사람이 서버마다 들어가서 띄우고 지켜볼 수는 없다.

- **컨테이너 이미지(image)**: 앱 jar, 그 jar를 돌릴 JRE, 필요한 라이브러리를 한 파일로 묶은 것이다.
- **컨테이너(container)**: 이미지를 실행한 것이다. 이미지 하나로 컨테이너를 여러 개 띄울 수 있고, 어느 서버에서 띄워도 똑같이 동작한다 `[문헌]`.
- **쿠버네티스(Kubernetes, K8s)**: 사람이 "주문 서비스를 2개 유지해라"라고 적어 두면, 알아서 빈 서버를 찾아 컨테이너를 띄우는 관리 시스템이다. 죽으면 다시 띄우고, 새 버전이 나오면 순서대로 바꾼다 `[문헌]`.

## 4. 핵심 — 두 종류의 관계

### 4-1. 실행 관계: 무엇이 무엇 위에서 도는가

큰 것에서 작은 것 순서로 적으면 다음과 같다.

1. **클러스터(cluster)**: 쿠버네티스가 관리하는 서버 전체 묶음이다.
2. **노드(node)**: 클러스터 안의 서버 한 대다. 실제 서버일 수도 있고 가상 머신일 수도 있다. 로컬 실습에 쓸 kind(Kubernetes IN Docker)에서는 Docker 컨테이너 하나가 노드 한 대 역할을 한다.
3. **Pod**: 노드 위에서 실행되는 최소 단위다. 쿠버네티스는 컨테이너를 직접 다루지 않고 항상 Pod로 감싸서 다룬다. Pod마다 자기 IP 주소가 있다.
4. **컨테이너**: Pod 안에서 실제로 앱이 실행되는 곳이다. 이 예제에서는 Pod 하나에 컨테이너 하나, 즉 Spring Boot 앱 하나가 들어간다.

실제 배치 예: 노드 A에서 주문 Pod 1개와 재고 Pod 1개가 돌고, 노드 B에서 주문 Pod 1개와 재고 Pod 1개가 돈다. **한 노드 위에 서로 다른 서비스의 Pod가 섞여 있어도 된다.** 어느 Pod를 어느 노드에 둘지는 쿠버네티스가 정한다 `[문헌]`.

**Pod 하나에 마이크로서비스를 여러 개 넣지 않는 이유**: Pod는 함께 배포되고, 함께 재시작되고, 함께 늘어나는 단위다. 두 서비스를 한 Pod에 넣으면 한쪽만 새 버전으로 배포하거나 한쪽만 개수를 늘릴 수 없다. 서비스를 쪼갠 이유가 사라진다 `[추론]`. 한 Pod에 컨테이너를 여럿 넣는 경우는 앱 옆에 보조 프로그램(로그 수집기 등)을 붙일 때이고, 이것을 **사이드카(sidecar)** 라고 부른다 `[문헌]`.

### 4-2. 관리 관계: 무엇이 무엇을 관리하고 가리키는가

**Deployment와 Service는 Pod를 담는 그릇이 아니다.** 둘 다 Pod에 대한 규칙을 적은 문서이고, Pod들을 이름표로 찾아서 가리킨다.

- **라벨(label)**: Pod에 붙이는 이름표다. 주문 Pod 두 개에는 `app=order`, 재고 Pod 두 개에는 `app=inventory`를 붙인다.
- **Deployment**: "`app=order` 이름표를 단 Pod를, 이 이미지로, 항상 2개 유지하라"는 규칙이다. 쿠버네티스는 이 규칙과 현재 상태를 계속 비교한다. Pod가 하나 죽어서 1개가 되면 하나를 새로 만든다. 같은 이미지로 띄운 이 Pod들을 **복제본(replica)** 이라고 부른다.
- **Service**: "`app=inventory` 이름표를 단 Pod들에게 `inventory`라는 고정 이름을 붙이고, 들어온 요청을 그중 하나에 나눠 보내라"는 규칙이다.

그러니까 주문 서비스 하나는 쿠버네티스에서 세 가지로 나타난다.

- Pod 2개 — 실제로 실행된다.
- Deployment 1개 — Pod 개수를 유지한다.
- Service 1개 — Pod들 앞에서 고정 이름을 붙이고 요청을 나눈다.

셋을 이어 주는 것은 `app=order`라는 라벨이다. 재고 서비스도 똑같이 세 가지로 나타난다.

**용어 충돌 주의**: MSA에서 "서비스"는 마이크로서비스(따로 배포되는 앱 하나)를 뜻한다. 쿠버네티스에서 "Service"는 위에서 설명한 객체를 뜻한다. 이 문서에서는 쿠버네티스 객체를 가리킬 때 영어로 Service라고 쓴다.

### 4-3. Service가 따로 필요한 이유

Pod는 영구적이지 않다. 죽거나 새 버전으로 바뀌면 기존 Pod가 되살아나는 것이 아니라 **새 이름과 새 IP를 가진 새 Pod**가 생긴다 `[문헌]`. 주문 서비스가 재고 Pod의 IP를 직접 적어 두고 호출하면, 재고 Pod가 바뀌는 순간 호출이 실패한다.

그래서 주문 서비스는 `http://inventory:8080`처럼 Service 이름으로 호출한다. 뒤의 Pod가 바뀌면 Service가 가리키는 대상 목록이 자동으로 갱신되므로, 호출하는 쪽은 아무것도 바꿀 필요가 없다. 호출할 대상의 현재 주소를 찾아 주는 이 기능을 **서비스 디스커버리(service discovery)** 라고 한다. 쿠버네티스에서는 Service가 이 일을 하므로 Eureka 같은 별도 서버가 필요 없다 `[문헌]`.

## 5. 주문 한 건이 처리되는 흐름

고객이 상품 A를 3개 주문하는 경우다.

1. 고객의 요청이 클러스터 입구에 도착한다. 입구는 **Gateway API**(클러스터 밖에서 들어온 요청을 경로 규칙에 따라 Service로 보내는 쿠버네티스 표준 규격)로 만든다. 경로가 `/orders`로 시작하므로 이 요청은 `order` Service로 간다.
2. `order` Service가 주문 Pod 2개 중 하나를 골라 요청을 넘긴다.
3. 요청을 받은 주문 Pod는 `http://inventory:8080`으로 "주문 번호 1001, 상품 A, 3개 예약"을 요청한다.
4. `inventory` Service가 재고 Pod 2개 중 하나를 골라 요청을 넘긴다. 앞에서 주문 Pod가 어느 것이었는지와 관계없이 고른다.
5. 재고 Pod는 재고 DB에서 상품 A의 수량을 3개 줄이고 "성공"을 돌려준다.
6. 주문 Pod는 주문 DB에 "주문 1001, 확정"을 저장하고 고객에게 응답한다.

주문 Pod는 재고 DB에 직접 접속하지 않는다. 재고 데이터가 필요하면 반드시 재고 서비스의 API를 거친다. 이것이 **"서비스마다 자기 DB를 가진다"** 는 원칙이다.

## 6. 구현할 때 고려해야 하는 상황

### ① 네트워크 호출은 실패할 수 있다

메서드 호출은 실패하지 않지만 HTTP 호출은 실패한다. 가장 까다로운 경우는 **요청은 처리됐는데 응답만 사라진 경우**다. 5절의 5단계에서 재고는 줄었는데, 응답이 주문 Pod에 도착하기 전에 네트워크가 끊겼다고 하자. 주문 Pod는 실패로 알고 다시 요청한다. 재고 서비스가 이것을 새 요청으로 처리하면 재고가 6개 줄어든다.

그래서 재고 서비스는 "주문 번호 1001은 이미 예약했다"를 기억하고 두 번째 요청은 무시해야 한다. 같은 요청을 여러 번 받아도 결과가 한 번 받은 것과 같게 만드는 이 성질을 **멱등성(idempotency)** 이라고 한다.

### ② 무한정 기다리면 안 된다

재고 서비스가 느려지거나 멈추면, 주문 Pod의 요청 처리 스레드가 응답을 기다리며 하나씩 묶인다. 스레드가 다 묶이면 주문 서비스도 멈춘다. 한 서비스의 장애가 다른 서비스로 번지는 것이다. 그래서 호출마다 **제한 시간(timeout)** 을 두고, 시간이 지나면 고객에게 "잠시 후 다시 시도" 같은 실패 응답을 빨리 돌려줘야 한다 `[문헌]`.

### ③ 두 DB를 하나의 트랜잭션으로 묶을 수 없다

재고는 줄었는데 주문 DB 저장이 실패하면, 주문 없이 재고만 줄어든 상태가 남는다. `@Transactional`은 한 DB 안에서만 작동하므로 이 상황을 막지 못한다. 이 문제는 각 서비스가 자기 트랜잭션을 먼저 끝내고, 뒤 단계가 실패하면 앞 단계를 취소하는 처리를 실행하는 방식(**Saga 패턴**)으로 푼다 `[문헌]`. 이 실습에서는 결제 서비스를 추가하는 나중 단계에서 다룬다.

### ④ Pod는 언제든 사라진다는 전제로 짠다

Pod의 메모리나 로컬 디스크에 데이터를 두면 Pod가 바뀔 때 사라진다. 또 Pod가 2개이므로 1번 Pod의 메모리에 둔 로그인 세션을 2번 Pod는 모른다. 그래서 남아야 하는 데이터는 모두 DB 같은 외부 저장소에 둔다. 이렇게 Pod 자체는 상태를 들고 있지 않게 만드는 것을 **무상태(stateless)** 라고 한다 `[문헌]`.

### ⑤ 시작과 종료를 정확히 알려야 한다

Spring Boot 앱은 뜨는 데 몇 초에서 수십 초가 걸린다. DB 연결도 되기 전에 요청이 들어오면 실패한다. 그래서 앱은 "이제 요청을 받을 준비가 됐다"를 쿠버네티스에 알려야 한다.

- **프로브(probe)**: 쿠버네티스가 Pod에 상태를 주기적으로 묻는 것이다. 두 종류가 있다.
  - **readiness 프로브**: "요청을 받을 준비가 됐나?" 실패하면 Service가 그 Pod에 요청을 보내지 않는다.
  - **liveness 프로브**: "살아 있나?" 실패하면 쿠버네티스가 그 컨테이너를 재시작한다.
- 이 질문에 답하는 것이 **Spring Boot Actuator**(실행 중인 앱이 자기 상태를 HTTP로 보여 주는 기능)의 health 엔드포인트다 `[문헌]`.

종료할 때도 마찬가지다. 쿠버네티스가 Pod를 내리라고 신호를 보내면, 앱은 새 요청은 받지 않고 처리 중인 요청은 끝낸 뒤 종료해야 한다. 이것을 **그레이스풀 셧다운(graceful shutdown)** 이라 하고, Spring Boot가 설정으로 지원한다 `[문헌]`.

### ⑥ 환경마다 다른 값은 이미지 밖에 둔다

DB 주소와 비밀번호는 로컬·개발·운영 환경마다 다르다. 이미지 안에 넣으면 환경마다 이미지를 따로 만들어야 한다. 그래서 이미지는 하나로 두고, 값은 쿠버네티스가 환경변수로 넣어 준다. 일반 설정값은 **ConfigMap**, 비밀번호 같은 값은 **Secret**이라는 쿠버네티스 객체에 적어 둔다 `[문헌]`.

### ⑦ API를 바꿀 때는 옛 버전과 공존해야 한다

주문과 재고는 따로 배포되므로, 배포 도중에는 옛 버전 주문 Pod가 새 버전 재고 Pod를 호출하는 순간이 반드시 생긴다. 그래서 재고 API의 필드를 지우거나 이름을 바꾸면 안 되고, 새 필드를 추가하는 식으로만 바꿔야 한다 `[추론]`.

## 7. 운영할 때 실제로 벌어지는 일

### 평상시

Deployment는 서비스마다 Pod 2개를 유지한다. Service는 요청을 두 Pod에 나눠 보낸다. 두 Pod가 받는 요청 수는 대략 비슷해진다.

### 재고 Pod 하나가 죽었을 때 (예: 메모리 부족)

1. Service가 죽은 Pod를 요청 대상 목록에서 뺀다.
2. 그동안 남은 재고 Pod 하나가 모든 요청을 처리한다.
3. Deployment는 Pod가 1개뿐인 것을 보고 새 Pod를 만든다.
4. 새 Pod가 준비 완료(readiness)를 알리면 다시 요청을 받기 시작한다.

고객은 대부분 아무것도 모르고 지나간다. **Pod를 2개 이상 두는 이유가 이것이다.** 하나였다면 새 Pod가 뜰 때까지 재고 서비스가 멈춘다.

### 프로세스는 살아 있는데 앱이 멈췄을 때 (예: 교착 상태)

프로세스가 살아 있으니 겉으로는 정상처럼 보인다. 쿠버네티스는 주기적으로 Actuator health 엔드포인트를 호출하고(liveness 프로브), 응답이 없으면 그 컨테이너를 재시작한다 `[문헌]`.

### 새 버전을 배포할 때

쿠버네티스는 기본적으로 Pod를 한 번에 바꾸지 않고 하나씩 바꾼다. 새 버전 Pod를 하나 띄우고, 준비 완료가 확인되면 옛 버전 Pod를 하나 내린다. 이것을 반복한다. 이 방식을 **롤링 업데이트(rolling update)** 라고 하며, 서비스가 멈추지 않는다.

새 버전이 준비 완료를 끝내 알리지 못하면 교체가 멈추고 옛 버전이 계속 요청을 처리한다. 명령 하나로 이전 버전으로 되돌릴 수도 있다 `[문헌]`.

### 연말 세일로 주문이 몰릴 때

주문 Deployment의 개수를 2에서 5로 바꾸면 주문 Pod가 5개가 된다. 재고 서비스는 그대로 둔다. 이것이 쪼갠 이득이다.

다만 Pod를 늘려도 DB는 하나 그대로다. 병목이 DB라면 Pod를 늘려도 빨라지지 않는다 `[추론]`.

### 재고 서비스 전체가 멈췄을 때

주문 서비스는 제한 시간 안에 실패를 돌려줘야 한다(6절 ②). 제한 시간이 없으면 주문 서비스까지 멈추고, 고객은 주문 화면조차 볼 수 없게 된다.

### 문제 원인을 찾을 때

모놀리스라면 로그 파일 하나를 보면 된다. 여기서는 주문 한 건의 로그가 주문 Pod 하나와 재고 Pod 하나에 나뉘어 남는다. 어느 Pod였는지도 매번 다르다. Pod가 이미 교체됐다면 그 Pod의 로그는 사라졌을 수도 있다.

그래서 두 가지가 필요해진다.

- 모든 Pod의 로그를 한곳에 모으는 것
- **분산 추적(distributed tracing)**: 요청 하나가 여러 서비스를 거친 경로를 하나로 묶어 보는 기법. 서비스끼리 HTTP 헤더로 같은 추적 번호(trace ID)를 넘기고, 로그 한 줄마다 그 번호를 남긴다. 표준 규격으로 **OpenTelemetry**를 쓴다 `[문헌]`.

## 8. 용어 정리

| 용어 | 뜻 |
|---|---|
| 모놀리스(monolith) | 모든 기능이 하나로 된 애플리케이션 |
| 마이크로서비스(microservice) | 업무 영역별로 쪼개 따로 배포·확장되고 자기 DB를 가지는 앱 |
| 컨테이너 이미지(image) | 앱, 실행 환경, 라이브러리를 한 파일로 묶은 것 |
| 컨테이너(container) | 이미지를 실행한 것 |
| 쿠버네티스(Kubernetes, K8s) | 컨테이너를 서버에 배치하고, 죽으면 다시 띄우고, 개수를 유지하는 관리 시스템 |
| 클러스터(cluster) | 쿠버네티스가 관리하는 서버 전체 묶음 |
| 노드(node) | 클러스터 안의 서버 한 대 |
| kind | Docker 컨테이너를 노드로 써서 로컬에 쿠버네티스 클러스터를 만드는 도구 |
| Pod | 쿠버네티스가 실행하는 최소 단위. 컨테이너를 감싸고 자기 IP를 가진다 |
| 사이드카(sidecar) | 앱과 같은 Pod에 붙여 넣는 보조 프로그램 컨테이너 |
| 라벨(label) | Pod에 붙이는 이름표. Deployment와 Service가 이것으로 Pod를 찾는다 |
| Deployment | 어떤 라벨의 Pod를 어떤 이미지로 몇 개 유지할지 적은 규칙 |
| 복제본(replica) | 같은 이미지로 띄운 Pod들 각각 |
| Service (쿠버네티스) | 어떤 라벨의 Pod들에 고정 이름을 붙이고 요청을 나눠 보내는 규칙 |
| 서비스 디스커버리(service discovery) | 호출할 대상의 현재 주소를 찾아 주는 기능 |
| Gateway API | 클러스터 밖 요청을 경로 규칙에 따라 Service로 보내는 쿠버네티스 표준 규격 |
| 멱등성(idempotency) | 같은 요청을 여러 번 받아도 결과가 한 번 받은 것과 같은 성질 |
| 제한 시간(timeout) | 응답을 기다리는 최대 시간. 넘으면 실패로 처리한다 |
| Saga 패턴 | 서비스별 트랜잭션을 차례로 끝내고, 실패하면 앞 단계를 취소 처리로 되돌리는 방식 |
| 무상태(stateless) | Pod가 남아야 할 데이터를 자기 안에 두지 않고 외부 저장소에 두는 것 |
| 프로브(probe) | 쿠버네티스가 Pod 상태를 주기적으로 묻는 것 |
| readiness 프로브 | 요청 받을 준비가 됐는지 묻는다. 실패하면 요청을 보내지 않는다 |
| liveness 프로브 | 살아 있는지 묻는다. 실패하면 컨테이너를 재시작한다 |
| Spring Boot Actuator | 실행 중인 앱이 자기 상태를 HTTP로 보여 주는 기능. 프로브에 응답한다 |
| 그레이스풀 셧다운(graceful shutdown) | 종료 신호를 받으면 새 요청은 거절하고 처리 중인 요청은 끝낸 뒤 종료하는 것 |
| ConfigMap / Secret | 환경마다 다른 설정값 / 비밀번호 같은 값을 이미지 밖에 적어 두는 쿠버네티스 객체 |
| 롤링 업데이트(rolling update) | Pod를 하나씩 새 버전으로 교체해 서비스를 멈추지 않고 배포하는 방식 |
| 분산 추적(distributed tracing) | 요청 하나가 여러 서비스를 거친 경로를 하나로 묶어 보는 기법 |
| OpenTelemetry | 추적·메트릭·로그를 내보내는 방식의 업계 표준 규격이자 라이브러리 |
