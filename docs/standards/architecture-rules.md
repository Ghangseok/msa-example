# 아키텍처 규칙

- 상태: 초안 (2026-10-04)
- 출처: P = [마이크로서비스와 쿠버네티스 기초](../references/msa-k8s-primer.md), [ADR-0001](../adr/0001-single-speckit-at-root.md)
- 쓰는 곳: `/speckit-constitution`의 입력. 헌법(`.specify/memory/constitution.md`)은 이 문서의 **반드시** 규칙을 원칙으로 삼는다.

모든 서비스에 공통인 규칙이다. 한 서비스에만 해당하는 규칙(패키지 구조, DB 스키마 규칙 등)은 `services/<svc>/CLAUDE.md`에 적는다.

수준: **반드시**는 어기면 리뷰에서 막는다. **권장**은 어길 때 plan.md의 Complexity Tracking에 이유를 적는다.

## 1. 서비스 경계

| ID | 수준 | 규칙 | 이유 | 출처 |
|---|---|---|---|---|
| STD-001 | 반드시 | 서비스마다 자기 DB를 가진다. 다른 서비스의 DB에 접속하지 않고, 필요한 데이터는 그 서비스의 API로 얻는다 | DB를 나누지 않으면 따로 배포하고 따로 바꿀 수 없다 | P§5 |
| STD-002 | 반드시 | Pod 하나에는 마이크로서비스 하나만 넣는다. 여러 컨테이너는 로그 수집기 같은 사이드카일 때만 허용한다 | 한 Pod에 넣으면 따로 배포·확장할 수 없다 | P§4-1 |
| STD-015 | 반드시 | `libs/`에는 여러 서비스가 꼭 함께 써야 하는 기술 코드(추적 설정 등)만 둔다. 도메인 규칙, DTO, Mapper와 SQL은 공유하지 않는다 | 공유가 늘면 서비스끼리 엮여 따로 배포할 수 없게 된다 | ADR-0001 `[추론]` |

## 2. 서비스 사이 호출

| ID | 수준 | 규칙 | 이유 | 출처 |
|---|---|---|---|---|
| STD-003 | 반드시 | 서비스 사이 호출은 쿠버네티스 Service 이름으로 한다(예: `http://inventory:8080`). Pod IP를 쓰지 않고, 별도 디스커버리 서버(Eureka 등)를 두지 않는다 | Pod는 바뀔 때마다 IP가 바뀐다 | P§4-3 |
| STD-004 | 반드시 | 모든 원격 호출에 연결 제한 시간과 응답 제한 시간을 둔다. 시간이 지나면 호출한 쪽은 기다리지 않고 실패 응답을 돌려준다. 값은 하드코딩하지 않고 설정으로 둔다 | 제한 시간이 없으면 한 서비스의 장애가 호출한 서비스로 번진다 | P§6-② |
| STD-005 | 반드시 | 상태를 바꾸는 서비스 사이 API는 멱등이어야 한다. 호출한 쪽은 재시도할 때 같은 멱등 키(예: 주문 번호)를 다시 보낸다 | 응답만 사라진 경우 재시도가 중복 처리된다 | P§6-① |
| STD-010 | 반드시 | API와 이벤트는 추가하는 방식으로만 바꾼다. 필드를 지우거나 이름·타입·뜻을 바꾸지 않는다. 깨는 변경이 꼭 필요하면 ADR을 먼저 쓴다 `[제안]` | 배포 중에는 옛 버전과 새 버전이 서로 호출한다 | P§6-⑦ |
| STD-014 | 반드시 | 서비스 사이 API와 이벤트를 바꾸면 같은 PR에서 `contracts/`의 현재본(OpenAPI, AsyncAPI)도 고친다 | `specs/NNN/contracts/`에는 그 기능에서 바뀐 부분만 있어 전체 계약을 알 수 없다 | ADR-0001 |
| STD-016 | 반드시 | 재시도는 멱등한 호출에만 한다. 연결 실패, 시도 제한 시간 초과, 502·503·504에만 재시도하고, 업무 결과(재고 부족)와 4xx에는 재시도하지 않는다. 재시도를 포함한 전체 시간은 정해진 한도를 넘지 않는다 | 멱등하지 않은 호출을 재시도하면 중복 처리된다. 업무 결과는 다시 물어도 같다 | OQ-004, P§6-① |
| STD-018 | 반드시 | 원격 호출을 DB 트랜잭션 안에서 하지 않는다. 호출 전후의 저장은 각각 별도 트랜잭션으로 끝낸다 | 호출을 기다리는 동안 DB 연결과 잠금을 잡고 있게 된다. 최대 30초 동안 잡힐 수 있다 | OQ-004 `[추론]` |
| STD-019 | 반드시 | 다른 서비스를 동기로 호출할 때는 서킷 브레이커를 둔다. 서킷이 열려 있으면 호출하지 않고 바로 실패하며, 재시도도 하지 않는다 | 상대 서비스가 오래 멈추면 호출하는 쪽의 스레드가 묶여 함께 멈춘다. Java 17이라 가상 스레드로 피할 수 없다 | OQ-009, P§6-② |

## 3. 실행과 배포

| ID | 수준 | 규칙 | 이유 | 출처 |
|---|---|---|---|---|
| STD-006 | 반드시 | 남아야 하는 데이터(세션 포함)를 Pod 메모리나 로컬 디스크에 두지 않는다. DB 같은 외부 저장소에 둔다 | Pod는 언제든 사라지고, Pod끼리 메모리를 공유하지 않는다 | P§6-④ |
| STD-007 | 반드시 | Actuator health로 readiness와 liveness를 노출하고, Deployment에 두 프로브를 모두 설정한다. liveness에는 외부 시스템(DB, 다른 서비스) 상태를 넣지 않는다 | 준비 전 요청과 교착을 막는다. liveness가 외부 장애에 반응하면 모든 Pod가 함께 재시작된다 | P§6-⑤, P§7, Spring Boot 문서 `[문헌]` |
| STD-008 | 반드시 | 그레이스풀 셧다운을 켠다. 앱의 종료 대기 시간(`spring.lifecycle.timeout-per-shutdown-phase`)은 Pod의 `terminationGracePeriodSeconds`보다 짧게 둔다. Spring Boot 버전마다 기본값이 다를 수 있으므로 설정에 명시한다 | 처리 중인 요청이 끊기지 않게 한다. 대기 시간이 더 길면 쿠버네티스가 먼저 강제 종료한다 | P§6-⑤ `[추론]` |
| STD-009 | 반드시 | 이미지는 서비스마다 하나다. 환경마다 다른 값은 ConfigMap, 비밀값은 Secret에 두고 환경변수로 받는다. 이미지와 저장소에 비밀번호를 넣지 않는다 | 환경마다 이미지를 따로 만들지 않기 위해서다 | P§6-⑥ |
| STD-011 | 반드시 | 서비스마다 replicas를 2 이상으로 둔다 | 하나면 새 Pod가 뜰 때까지 서비스가 멈춘다 | P§7 |

## 4. 관측성

| ID | 수준 | 규칙 | 이유 | 출처 |
|---|---|---|---|---|
| STD-012 | 반드시 | 서비스 사이 호출에 추적 정보를 넘기고, 로그 한 줄마다 trace ID를 남긴다. OpenTelemetry를 쓴다 | 주문 한 건의 로그가 여러 Pod에 나뉘어 남는다 | P§7 |
| STD-013 | 반드시 | 로그를 Pod 안 파일에 쓰지 않는다. 표준 출력으로 내보내고, 같은 로그를 OTLP로 관측 저장소(`grafana/otel-lgtm`)에도 보낸다 | Pod가 교체되면 Pod 안 로그는 사라진다. 저장소에 모아야 trace ID로 여러 서비스의 로그를 함께 찾는다 | P§7, design 10절 |

## 5. 보안

| ID | 수준 | 규칙 | 이유 | 출처 |
|---|---|---|---|---|
| STD-017 | 반드시 | 외부에 열린 API는 Keycloak이 발급한 JWT를 서비스가 직접 검증한다(OAuth2 Resource Server). 사용자 식별은 토큰의 `sub`로 하고, 요청 본문이나 별도 헤더로 받은 사용자 ID를 믿지 않는다 | Gateway를 거치지 않은 요청도 막고, 사용자 위조를 막는다 | OQ-007, ADR-0006 |
