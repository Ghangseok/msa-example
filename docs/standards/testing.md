# 테스트 전략

- 상태: **확정 (2026-10-04)** — B안(서비스 통합 중심 + 계약 + kind E2E)
- 쓰는 곳: `/speckit-constitution`(테스트 원칙), `/speckit-tasks`(테스트 작업 순서)

## 1. 세 가지 안

| | A안: 단위 중심 피라미드 + H2 | **B안: 서비스 통합 중심 + 계약 + kind E2E** | C안: E2E 중심 |
|---|---|---|---|
| 중심 | 단위 테스트를 많이, 통합은 적게 | 서비스 하나를 실제 DB와 함께 띄운 통합 테스트 | kind에 올린 전체 시스템을 밖에서 호출 |
| DB | H2 (Oracle 호환 모드) | Testcontainers로 띄운 Oracle 21c XE | 실제 Oracle |
| 상대 서비스 | Mockito 목 | WireMock (지연·오류·응답 유실을 흉내 냄) | 실제 서비스 |
| 계약 검증 | 없음 | `contracts/`의 OpenAPI로 양쪽 검증 | 없음 (E2E가 대신함) |
| 속도 | 가장 빠름 | 중간 (Oracle 컨테이너 기동 수십 초, 재사용으로 줄임) | 가장 느림 (이미지 빌드, 배포) |
| 장점 | 피드백이 빠르다 | 멱등성, 동시성, 재시도, 제한 시간을 실제와 같은 조건에서 정밀하게 검증한다 | 실제 운영과 가장 같다 |
| 약점 | H2는 Oracle과 잠금·시퀀스·SQL 방언이 달라서, 이 프로젝트의 핵심인 멱등·동시성 검증(TC-003, TC-005)을 믿을 수 없다. 목은 실제 HTTP 실패를 흉내 내지 못한다 | Docker가 떠 있어야 한다. 테스트 시간이 A안보다 길다 | 응답 유실, 정확히 2.5초 지연 같은 상황을 만들기 어렵다. 실패했을 때 어느 서비스 탓인지 찾기 어렵다 |

**B안을 고른 이유**: 이 프로젝트에서 검증하려는 것은 대부분 "서비스 경계에서 생기는 일"(멱등성, 제한 시간, 재시도, 동시 예약)이다. 이것은 실제 Oracle과 실제 HTTP가 있어야 의미 있게 확인되고, WireMock을 쓰면 지연과 오류를 원하는 대로 만들 수 있다. 쿠버네티스 동작(Pod 삭제, 롤링 업데이트)만 kind E2E로 따로 확인한다.

## 2. B안의 테스트 층

| 층 | 대상 | 도구 | 위치 | 실행 시점 |
|---|---|---|---|---|
| 단위 | `domain` 패키지의 업무 규칙(주문 상태 전이, 항목 검사, 멱등 판단), 재시도 일정 계산 | JUnit 5, AssertJ (Spring 없이) | `services/<svc>/src/test` | 매 빌드 |
| Mapper | MyBatis SQL이 실제 Oracle에서 맞게 도는지. 잠금, 조건부 갱신, 1:N 매핑, 19c 호환 SQL | `@MybatisTest` + Testcontainers(Oracle 21c XE) | `services/<svc>/src/test` | 매 빌드 |
| 서비스 통합 | API → service → DB 전 구간. 멱등, 동시 예약, 교착, 재시도, 제한 시간, 서킷 브레이커, 인증 | `@SpringBootTest`, Testcontainers(Oracle 21c XE), WireMock, Spring Security Test | `services/<svc>/src/test` | 매 빌드 |
| 계약 | 재고 API가 `contracts/`의 OpenAPI를 지키는지(제공자), 주문이 쓰는 WireMock 응답이 같은 OpenAPI를 따르는지(소비자) | OpenAPI 검증 라이브러리 (plan에서 확정) | 각 서비스 | 매 빌드 |
| 아키텍처 | 계층 의존 규칙(controller → service → mapper·client·domain, domain은 Spring·MyBatis를 모름) | ArchUnit | 각 서비스 | 매 빌드 |
| E2E·운영 | Gateway → 주문 → 재고 전체 흐름, TC-101~109 | kind, Keycloak 토큰, 부하 도구(plan에서 확정) | `tests/e2e/` | 수동 또는 별도 작업 |

## 3. 규칙

- **테스트 먼저**: tasks.md에서 인수 시나리오(TC)의 테스트 작업을 구현 작업보다 앞에 둔다. 테스트가 실패하는 것을 확인한 뒤 구현한다. 도메인 단위 테스트는 TDD를 권장한다.
- **TC 연결**: 인수 시나리오를 검증하는 테스트에는 TC ID를 남긴다. 예: `@DisplayName("TC-003 같은 주문으로 재요청해도 재고는 한 번만 줄어든다")`
- **기대값의 출처**: 인수 시나리오 테스트의 기대값은 사용자가 확정한 `docs/test-cases/`에서 그대로 가져온다. 구현하는 동안 기대값을 바꾸지 않는다. 기대값이 틀렸다고 판단되면 구현을 멈추고 사용자에게 묻는다. 헌법 "실제 조건에서 테스트 먼저" 원칙의 세부 규칙이다.
- **DB는 진짜 Oracle**: 영속성 테스트에 H2를 쓰지 않는다. MyBatis는 SQL을 그대로 보내므로 Oracle 문법과 잠금 동작은 Oracle에서만 확인된다. Oracle 컨테이너는 서비스의 테스트 전체에서 하나를 재사용해 기동 시간을 줄인다. 서비스마다 자기 컨테이너를 쓰는 것은 운영 구성(ADR-0005)과 같다.
- **상대 서비스는 WireMock**: 서비스 통합 테스트에서 다른 서비스를 실제로 띄우지 않는다.
- **인증**: 서비스 통합 테스트는 Keycloak 없이 Spring Security Test의 JWT 지원으로 사용자를 흉내 낸다. 실제 토큰 발급은 E2E에서만 확인한다.
- **시간**: 재시도 대기와 제한 시간 테스트가 실제로 30초씩 걸리지 않도록, 대기 시간을 설정값으로 두고 테스트에서는 짧게 바꾼다. 단, 기본값(OQ-004)이 설정에 맞게 들어갔는지는 단위 테스트로 따로 확인한다.
- **커버리지**: 수치 목표는 두지 않는다. 모든 TC와 BR이 어떤 테스트로 검증되는지 연결되어 있는지로 판단한다.

## 4. 테스트 데이터

- 운영·로컬용 초기 데이터(상품 재고, OQ-001)는 Flyway로 넣는다.
- 테스트는 자기가 쓸 데이터를 직접 넣고, 다른 테스트의 데이터에 기대지 않는다.
- E2E에서 재고를 정해진 값으로 맞추는 방법(DB 직접 조작, 테스트 전용 프로필 등)은 plan에서 정한다.
