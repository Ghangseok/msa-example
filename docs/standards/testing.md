# 테스트 전략

- 상태: **확정 (2026-10-04, 2026-10-07 단위·계약 행의 도구를 001 plan에 맞춤)** — B안(서비스 통합 중심 + 계약 + kind E2E)
- 쓰는 곳: `/speckit-constitution`(테스트 원칙), `/speckit-tasks`(테스트 작업 순서)

## 1. 세 가지 안

| | A안: 단위 중심 피라미드 + H2 | **B안: 서비스 통합 중심 + 계약 + kind E2E** | C안: E2E 중심 |
|---|---|---|---|
| 중심 | 단위 테스트를 많이, 통합은 적게 | 서비스 하나를 실제 DB와 함께 띄운 통합 테스트 | kind에 올린 전체 시스템을 밖에서 호출 |
| DB | H2 (Oracle 호환 모드) | Testcontainers로 띄운 Oracle 21c XE | 실제 Oracle |
| 상대 서비스 | Mockito 목 | WireMock (지연·오류·응답 유실을 흉내 냄) | 실제 서비스 |
| 계약 검증 | 없음 | `contracts/`의 OpenAPI로 양쪽 검증 | 없음 (E2E가 대신함) |
| 속도 | 가장 빠름 | 중간 (Oracle 컨테이너 기동 수십 초, 재사용으로 줄임) | 가장 느림 (이미지 빌드, 배포) |
| 장점 | 피드백이 빠르다 | 멱등성, 동시성, 재시도, 제한 시간을 실제와 같은 조건에서 정밀하게 검증한다 | 실제 운영과 가장 같다 |
| 약점 | H2는 Oracle과 잠금·시퀀스·SQL 방언이 달라서, 이 프로젝트의 핵심인 멱등·동시성 검증(TC-003, TC-005)을 믿을 수 없다. 목은 실제 HTTP 실패를 흉내 내지 못한다 | Docker가 떠 있어야 한다. 테스트 시간이 A안보다 길다 | 응답 유실, 정확히 2.5초 지연 같은 상황을 만들기 어렵다. 실패했을 때 어느 서비스 탓인지 찾기 어렵다 |

**B안을 고른 이유**: 이 프로젝트에서 검증하려는 것은 대부분 "서비스 경계에서 생기는 일"(멱등성, 제한 시간, 재시도, 동시 예약)이다. 이것은 실제 Oracle과 실제 HTTP가 있어야 의미 있게 확인되고, WireMock을 쓰면 지연과 오류를 원하는 대로 만들 수 있다. 쿠버네티스 동작(Pod 삭제, 롤링 업데이트)만 kind E2E로 따로 확인한다.

## 2. B안의 테스트 층

| 층 | 대상 | 도구 | 위치 | 실행 시점 |
|---|---|---|---|---|
| 단위 | `domain` 패키지의 업무 규칙(주문 상태 전이, 항목 검사, 멱등 판단), 재시도 일정 계산 | JUnit Jupiter 6, AssertJ (Spring 없이) | `services/<svc>/src/test` | 매 빌드 |
| Mapper | MyBatis SQL이 실제 Oracle에서 맞게 도는지. 잠금, 조건부 갱신, 1:N 매핑, 19c 호환 SQL | `@MybatisTest` + Testcontainers(Oracle 21c XE) | `services/<svc>/src/test` | 매 빌드 |
| 서비스 통합 | API → service → DB 전 구간. 멱등, 동시 예약, 교착, 재시도, 제한 시간, 서킷 브레이커, 인증 | `@SpringBootTest`, Testcontainers(Oracle 21c XE), WireMock, Spring Security Test | `services/<svc>/src/test` | 매 빌드 |
| 계약 | 재고 API가 `contracts/`의 OpenAPI를 지키는지(제공자), 주문이 쓰는 WireMock 응답이 같은 OpenAPI를 따르는지(소비자) | swagger-request-validator-core 2.46.1. 요청과 응답을 검증기 형식으로 옮기는 작은 도우미를 서비스마다 둔다 (001 plan, `specs/001-place-order/research.md` 결정 12) | 각 서비스 | 매 빌드 |
| 아키텍처 | 계층 의존 규칙(controller → service → mapper·client·domain, domain은 Spring·MyBatis를 모름), 그리고 `coding-conventions.md` 3-8절의 기계 검사 | ArchUnit, 소스·XML 글자 검사, Gradle 의존성 검사 | 각 서비스 | 매 빌드 |
| 정적 분석 | 일반 버그 패턴 | SpotBugs | 각 서비스 | 매 빌드 |
| E2E·운영 | Gateway → 주문 → 재고 전체 흐름, TC-101~109 | kind, Keycloak 토큰, 부하 도구(plan에서 확정) | `tests/e2e/` | 수동 또는 별도 작업 |

## 3. 규칙

- **테스트 먼저**: tasks.md에서 인수 시나리오(TC)의 테스트 작업을 구현 작업보다 앞에 둔다. 테스트가 실패하는 것을 확인한 뒤 구현한다. 도메인 단위 테스트는 TDD를 권장한다.
- **TC 연결**: 인수 시나리오를 검증하는 테스트에는 TC ID를 남긴다. 예: `@DisplayName("TC-003 같은 주문으로 재요청해도 재고는 한 번만 줄어든다")`
- **기대값의 출처**: 인수 시나리오 테스트의 기대값은 사용자가 확정한 `docs/test-cases/`에서 그대로 가져온다. 구현하는 동안 기대값을 바꾸지 않는다. 기대값이 틀렸다고 판단되면 구현을 멈추고 사용자에게 묻는다. 헌법 "실제 조건에서 테스트 먼저" 원칙의 세부 규칙이다.
- **DB는 진짜 Oracle**: 영속성 테스트에 H2를 쓰지 않는다. MyBatis는 SQL을 그대로 보내므로 Oracle 문법과 잠금 동작은 Oracle에서만 확인된다. Oracle 컨테이너는 서비스의 테스트 전체에서 하나를 재사용해 기동 시간을 줄인다. 서비스마다 자기 컨테이너를 쓰는 것은 운영 구성(ADR-0005)과 같다.
- **상대 서비스는 WireMock**: 서비스 통합 테스트에서 다른 서비스를 실제로 띄우지 않는다.
- **인증**: 서비스 통합 테스트는 Keycloak 없이 Spring Security Test의 JWT 지원으로 사용자를 흉내 낸다. 실제 토큰 발급은 E2E에서만 확인한다.
- **시간**: 재시도 대기와 제한 시간 테스트가 실제로 30초씩 걸리지 않도록, 대기 시간을 설정값으로 두고 테스트에서는 짧게 바꾼다. 단, 기본값(OQ-004)이 설정에 맞게 들어갔는지는 단위 테스트로 따로 확인한다.
- **커버리지**: 수치 목표는 두지 않는다. 모든 TC와 BR이 어떤 테스트로 검증되는지 연결되어 있는지로 판단한다.
- **검사를 끄는 표시**: `@Disabled`, `@SuppressWarnings` 같은 검사를 끄는 표시는 허용 목록에 있어야 한다. 허용 목록은 사용자가 PR에서 승인한다. 찾는 표시의 목록은 `coding-conventions.md` 3-8절에 있다.

## 4. 테스트 데이터

- 운영·로컬용 초기 데이터(상품 재고, OQ-001)는 Flyway로 넣는다.
- 테스트는 자기가 쓸 데이터를 직접 넣고, 다른 테스트의 데이터에 기대지 않는다.
- E2E에서 재고를 정해진 값으로 맞출 때는 테스트 코드가 재고 DB(`inventory-db`)에 직접 접속해서, 테스트마다 전용 상품 행을 넣고 끝나면 지운다. 재고 서비스에 테스트 전용 API를 만들지 않는다. (2026-10-05 결정)

## 용어

- **테스트 피라미드 (test pyramid)**: 빠른 단위 테스트를 가장 많이, 느린 통합 테스트와 E2E 테스트를 가장 적게 두는 테스트 구성이다. 이 프로젝트는 이것(A안) 대신 서비스 통합 테스트를 중심에 둔다(B안).
- **H2**: Java로 만든 가벼운 메모리 DB다. Oracle과 잠금, 시퀀스, SQL 문법이 달라서 이 프로젝트의 테스트에는 쓰지 않는다.
- **목 (mock)**: 테스트에서 진짜 객체 대신 넣는, 정해진 대로만 답하는 가짜 객체다(예: Mockito). 실제 HTTP 실패를 흉내 내지 못해서, 상대 서비스는 목이 아니라 WireMock으로 흉내 낸다.
- **단위 테스트 (unit test)**: 클래스나 메서드 하나를 Spring이나 DB 없이 따로 확인하는 테스트다. `domain` 패키지의 업무 규칙을 이것으로 확인한다.
- **Mapper 테스트 (mapper test)**: MyBatis SQL이 실제 Oracle에서 맞게 도는지 확인하는 테스트다. 잠금, 조건부 갱신, 19c 호환 SQL을 확인한다.
- **서비스 통합 테스트 (service integration test)**: 서비스 하나를 실제 DB와 함께 띄우고 API부터 DB까지 확인하는 테스트다. 상대 서비스는 WireMock으로 대신한다.
- **계약 테스트 (contract test)**: API가 명세(OpenAPI)대로 요청과 응답을 주고받는지 확인하는 테스트다. 재고 API와 주문 서비스의 WireMock 응답이 `contracts/`를 따르는지 확인한다.
- **제공자 / 소비자 (provider / consumer)**: 계약 테스트에서 API를 내주는 쪽과 부르는 쪽이다. 재고 서비스가 제공자이고 주문 서비스가 소비자다.
- **아키텍처 테스트 (architecture test)**: 코드가 계층 의존 방향 같은 구조 규칙을 지키는지 검사하는 테스트다. ArchUnit과 소스 글자 검사로 한다.
- **정적 분석 (static analysis)**: 프로그램을 실행하지 않고 소스나 클래스 파일만 읽어 문제를 찾는 검사다. 이 저장소에서는 SpotBugs를 쓴다.
- **E2E 테스트 (end-to-end test)**: 실제로 배포한 시스템을 밖에서 호출해 처음부터 끝까지 확인하는 테스트다. `tests/e2e/`에 두고 kind 클러스터에서 돌린다.
- **Testcontainers**: 테스트를 실행할 때 Docker 컨테이너를 띄우고 끝나면 지우는 라이브러리다. 실제 Oracle에서 테스트하려고 쓴다.
- **WireMock**: 다른 서비스인 척 정해진 응답이나 지연, 오류를 돌려주는 테스트용 가짜 서버다. 서비스 통합 테스트에서 재고 서비스 대신 쓴다.
- **`@MybatisTest`**: mybatis-spring-boot-starter-test가 주는 애너테이션으로, MyBatis Mapper만 띄워 SQL을 시험한다. Mapper 테스트에서 실제 Oracle과 함께 쓴다.
- **`@SpringBootTest`**: 테스트할 때 Spring Boot 앱 전체를 띄우는 애너테이션이다. 서비스 통합 테스트에서 쓴다.
- **Spring Security Test**: 테스트에서 로그인한 사용자나 JWT를 흉내 내게 해 주는 Spring 모듈이다. 서비스 통합 테스트에서 Keycloak 없이 고객과 관리자를 흉내 낸다.
- **ArchUnit**: 패키지와 클래스 사이의 의존 규칙을 테스트 코드로 검사하는 라이브러리다. 계층 규칙과 일부 기계 검사를 이것으로 한다.
- **SpotBugs**: 컴파일된 클래스 파일을 읽어 흔한 버그 패턴을 찾는 정적 분석 도구다. 매 빌드에서 Gradle 플러그인으로 돌린다.
- **TDD (test-driven development)**: 실패하는 테스트를 먼저 쓰고, 그 테스트를 통과시키는 코드를 나중에 쓰는 개발 방식이다. 도메인 단위 테스트에 권장한다.
- **`@DisplayName`**: JUnit Jupiter에서 테스트에 사람이 읽을 이름을 붙이는 애너테이션이다. 인수 시나리오 테스트는 이 이름을 테스트 케이스 번호로 시작한다.
- **커버리지 (coverage)**: 테스트가 실행한 코드의 비율이다. 이 프로젝트는 수치 목표를 두지 않고, 모든 테스트 케이스와 업무 규칙이 테스트와 연결됐는지로 판단한다.
- **허용 목록 (allowlist)**: 규칙의 예외로 승인한 것만 적어 둔 파일이다. 이 저장소에서는 검사를 끄는 표시와 `${}` 예외를 적고, 사용자가 PR에서 승인한다.
- **응답 유실 (lost response)**: 상대 서비스는 요청을 처리했는데 응답이 돌아오지 못하고 사라지는 일이다. 이때 다시 보낸 요청이 두 번 처리되지 않게 멱등성으로 막는다.
- **부하 도구 (load testing tool)**: 정해진 속도로 요청을 계속 보내는 프로그램이다. 운영 테스트에서 쓰고, 무엇을 쓸지는 plan에서 정한다.
- **멱등성 (idempotency)**: 같은 요청을 여러 번 받아도 결과가 한 번 받은 것과 같은 성질이다. 재고 예약은 주문 번호로, 주문 생성은 주문 요청 키로 같은 요청인지 알아본다.
- **교착 (deadlock)**: 두 작업이 서로 상대가 잡은 잠금을 기다리며 둘 다 멈추는 상태다. 이 프로젝트는 재고 행을 언제나 상품 ID 순서로 잠가서 교착을 막는다.
- **서킷 브레이커 (circuit breaker)**: 상대 서비스 호출이 계속 실패하면 한동안 호출을 멈추고 바로 실패를 돌려주는 장치다. 재고 서비스가 멈췄을 때 주문 서비스까지 멈추지 않게 막는다.
- **초기 데이터 (seed data)**: 서비스를 처음 띄울 때 DB에 미리 넣어 두는 데이터다. 상품 재고는 API 없이 초기 데이터로만 넣는다.
