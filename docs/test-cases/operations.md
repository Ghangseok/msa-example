# 테스트 케이스 — 운영 상황

- 상태: **확정 (2026-10-05)**
- 출처: P = [마이크로서비스와 쿠버네티스 기초](../references/msa-k8s-primer.md) 7절
- 대상: [NFR-001~008](../requirements/non-functional.md)
- 구현 위치: `tests/e2e/`. kind 클러스터에 두 서비스를 올린 상태에서 돌린다.

공통 전제:

- 주문 서비스와 재고 서비스가 각각 Pod 2개로 떠 있고, 둘 다 readiness를 통과했다.
- "부하 중"은 주문 요청을 초당 10건씩 계속 보내는 상태다. 부하 도구는 plan에서 정한다.
- 따로 적지 않으면 허용 실패는 0건이다. 시간 기대값의 허용 오차와 health "정상"의 뜻은 `docs/test-cases/order-placement.md`의 공통 전제를 따른다.

## TC-101 재고 Pod 하나가 사라져도 주문은 계속 처리된다

- 관련: NFR-001, STD-011
- **Given** 부하 중이다
- **When** 재고 Pod 하나를 강제로 지운다 (`kubectl delete pod <재고 Pod> --grace-period=0 --force`)
- **Then** 주문 요청은 하나도 실패하지 않는다
- **And** Deployment가 새 재고 Pod를 만들고, 새 Pod가 readiness를 통과하면 다시 요청을 받는다
- **And** 60초 안에 재고 Pod는 다시 2개다

## TC-102 응답하지 않는 컨테이너는 재시작된다

- 관련: NFR-006, STD-007
- **Given** 재고 Pod 하나를 "프로세스는 살아 있지만 응답하지 않는" 상태로 만든다
- **When** liveness 프로브가 정해진 횟수만큼 실패한다
- **Then** 응답하지 않게 된 뒤 30초 안에 쿠버네티스가 그 컨테이너를 재시작한다 (Pod의 RESTARTS 값이 1 오른다)
- **And** 재시작을 시작한 뒤 90초 안에 그 Pod가 다시 readiness를 통과한다
- 비고: 교착을 그대로 만들기는 어렵다. 이 상태를 만드는 방법은 plan에서 정한다. 후보 ① liveness 상태를 BROKEN으로 바꾸는 테스트 전용 엔드포인트. 이때 health는 바로 503을 응답하므로 "응답하지 않는" 상황과는 다르다. 후보 ② 요청 스레드를 모두 묶어 프로브가 시간 초과로 실패하게 하는 테스트 전용 엔드포인트.

## TC-103 롤링 업데이트 중에도 요청이 실패하지 않는다

- 관련: NFR-003, STD-007, STD-008
- **Given** 부하 중이다
- **When** 재고 Deployment의 이미지를 새 버전으로 바꾼다
- **Then** Pod가 하나씩 새 버전으로 바뀐다
- **And** 그동안 주문 요청은 하나도 실패하지 않는다
- 비고: Pod를 Service 대상에서 빼는 일과 종료 신호를 보내는 일이 동시에 일어나서, 종료 중인 Pod로 요청 몇 개가 갈 수 있다. 실패가 나오면 `preStop`에 짧은 대기를 넣는 방법을 검토한다. `[현장]`

## TC-104 준비되지 않는 새 버전은 교체가 멈추고, 되돌릴 수 있다

- 관련: NFR-003
- **Given** 부하 중이다
- **And** readiness를 끝내 통과하지 못하는 재고 이미지가 있다
- **When** 그 이미지로 재고 Deployment를 바꾼다
- **Then** 새 Pod는 요청을 받지 않고, 교체가 더 진행되지 않는다
- **And** 옛 버전 Pod가 요청을 계속 처리해 주문 요청은 하나도 실패하지 않는다
- **When** `kubectl rollout undo deployment/inventory`를 실행한다
- **Then** 재고 Deployment가 이전 버전으로 돌아간다

## TC-105 재고 서비스 전체가 멈춰도 주문 서비스는 살아 있다

- 관련: NFR-002, STD-004, OQ-009
- **Given** 재고 Deployment의 replicas를 0으로 줄였다
- **When** 고객이 주문한다
- **Then** 고객은 31초 안에 "잠시 후 다시 시도"를 받고, 주문은 "실패"로 기록된다
- **And** 주문 서비스의 health 확인은 계속 1초 안에 200으로 응답하고, 주문 Pod는 재시작되지 않는다
- **When** 재고가 멈춘 상태에서 주문을 초당 10건씩 1분 동안 넣는다
- **Then** 서킷이 열린 뒤의 주문은 1초 안에 실패 응답을 받는다 (STD-019)
- **And** 그동안 주문 서비스의 health 확인은 1초 안에 200으로 응답한다
- **When** 재고 replicas를 2로 되돌린다
- **Then** 재고 Pod가 다시 준비되고 서킷 열림 시간(10초)이 지나면 서킷이 닫히고 주문이 다시 성공한다
- 비고: 실험으로 서킷 브레이커를 끄고 같은 부하를 넣어, 요청 스레드가 바닥나 health 확인까지 늦어지는 것을 비교해 볼 수 있다.

## TC-106 배포 중 옛 버전 주문이 새 버전 재고를 호출해도 성공한다

- 관련: NFR-004, STD-010, STD-014
- **Given** 재고 API에 응답 필드를 하나 추가한 새 버전 재고가 떠 있다
- **And** 주문은 새 필드를 모르는 옛 버전이다
- **When** 고객이 주문한다
- **Then** 주문이 정상으로 확정된다
- 비고: 반대로 새 버전 주문이 새 필드에 기대면, 옛 버전 재고가 남아 있는 동안 실패한다. 이때는 재고를 먼저 배포하고 주문을 나중에 배포해야 한다. `[추론]`

## TC-107 주문 서비스만 늘릴 수 있다

- 관련: NFR-005
- **Given** 주문 Pod 2개, 재고 Pod 2개다
- **When** 주문 Deployment의 replicas를 5로 바꾼다 (`kubectl scale deployment/order --replicas=5`)
- **Then** 주문 Pod는 5개가 되고 모두 요청을 받는다
- **And** 재고 Pod는 2개 그대로다

## TC-108 주문 한 건의 로그를 추적 번호 하나로 찾는다

- 관련: NFR-007, STD-012, STD-013
- **Given** 로그 수집과 분산 추적이 설정되어 있다
- **When** 고객이 주문 한 건을 넣고, 그 주문의 trace ID를 확인한다
- **Then** 그 trace ID로 검색하면 주문 Pod와 재고 Pod의 로그가 함께 나온다
- **And** 추적 화면에서 주문 → 재고 호출이 한 흐름으로 보인다
- **When** 그 요청을 처리한 Pod들을 지운다
- **Then** 같은 trace ID로 여전히 로그를 찾을 수 있다

## TC-109 재고 DB가 멈춰도 주문 조회는 계속된다

- 관련: NFR-002, STD-001, ADR-0005
- **Given** 주문 몇 건이 기록되어 있다
- **When** `inventory-db` 컨테이너를 멈춘다 (`docker stop inventory-db`)
- **Then** 재고 Pod는 readiness에 실패해 Service 대상에서 빠지고, 재시작되지는 않는다 (liveness에는 DB 상태를 넣지 않는다, STD-007)
- **And** 서킷이 열린 뒤의 새 주문은 1초 안에 "실패"를 받는다
- **And** 고객의 주문 조회(`GET /orders`)와 관리자 조회는 정상으로 응답한다
- **When** `inventory-db`를 다시 켠다
- **Then** 재고 Pod가 다시 준비되고, 서킷이 닫힌 뒤 새 주문이 "확정"된다
- 비고: 서비스마다 DB를 따로 둔 덕분에 할 수 있는 실험이다. DB가 하나였다면 주문 조회도 함께 멈춘다.

## 용어

- **E2E 테스트 (end-to-end test)**: 실제로 배포한 시스템을 밖에서 호출해 처음부터 끝까지 확인하는 테스트다. `tests/e2e/`에 두고 kind 클러스터에서 돌린다.
- **부하 (load)**: 서비스에 계속 들어오는 요청의 양이다. 운영 테스트에서 "부하 중"은 주문 요청을 초당 10건씩 계속 보내는 상태다.
- **Pod**: 쿠버네티스가 컨테이너를 실행하는 가장 작은 단위다. 언제든 지워지고 새로 만들어지므로, 남아야 하는 데이터를 Pod 안에 두지 않는다.
- **Deployment**: Pod를 정해진 개수만큼 유지하고 새 버전으로 바꿔 주는 쿠버네티스 객체다. 서비스마다 하나 두고 Pod 수를 2개로 둔다.
- **replicas**: Deployment가 유지하는 Pod 수다. 서비스마다 2 이상으로 둬서 Pod 하나가 사라져도 서비스가 멈추지 않게 한다.
- **쿠버네티스 Service (Kubernetes Service)**: 여러 Pod 앞에 고정된 이름과 주소를 붙여 주는 쿠버네티스 객체다. 주문 서비스는 `http://inventory:8080`으로 재고 서비스를 부른다.
- **kubectl**: 쿠버네티스 클러스터에 명령을 보내는 명령줄 도구다. Pod 삭제, Pod 수 변경, 되돌리기를 kubectl로 한다.
- **readiness 프로브 (readiness probe)**: 쿠버네티스가 Pod에 "요청을 받을 준비가 됐나"를 주기적으로 묻는 검사다. 실패하면 그 Pod에는 요청을 보내지 않는다.
- **liveness 프로브 (liveness probe)**: 쿠버네티스가 Pod에 "살아 있나"를 주기적으로 묻는 검사다. 정해진 횟수만큼 실패하면 컨테이너를 재시작한다.
- **RESTARTS**: `kubectl get pods`가 보여 주는, 컨테이너가 재시작된 횟수다. liveness 프로브 때문에 재시작됐는지 이 값으로 확인한다.
- **롤링 업데이트 (rolling update)**: Pod를 하나씩 새 버전으로 바꿔, 서비스를 멈추지 않고 배포하는 방식이다. 바꾸는 동안 옛 버전과 새 버전이 함께 요청을 처리한다.
- **되돌리기 (rollback)**: 배포한 새 버전을 이전 버전으로 돌려놓는 일이다. 이 프로젝트에서는 `kubectl rollout undo` 명령 하나로 한다.
- **그레이스풀 셧다운 (graceful shutdown)**: 종료 신호를 받으면 새 요청은 받지 않고, 처리 중인 요청을 끝낸 뒤 종료하는 방식이다. 배포나 확장으로 Pod가 내려갈 때 요청이 끊기지 않게 한다.
- **preStop**: 쿠버네티스가 컨테이너에 종료 신호를 보내기 직전에 실행하는 단계다. 짧은 대기를 넣으면 종료 중인 Pod로 요청이 가는 것을 줄일 수 있다.
- **확장 (scale out)**: 같은 서비스의 Pod 수를 늘려 더 많은 요청을 처리하게 하는 일이다. 주문 서비스의 Pod 수만 따로 바꿀 수 있어야 한다.
- **서킷 브레이커 (circuit breaker)**: 상대 서비스 호출이 계속 실패하면 한동안 호출을 멈추고 바로 실패를 돌려주는 장치다. 재고 서비스가 멈췄을 때 주문 서비스까지 멈추지 않게 막는다.
- **추적 ID (trace ID)**: 요청 하나에 붙여 여러 서비스를 따라다니게 하는 번호다. 이 번호로 여러 서비스의 로그를 한곳에서 함께 찾는다.
- **분산 추적 (distributed tracing)**: 요청 하나가 여러 서비스를 거친 경로를 한 흐름으로 이어 보는 기술이다. 추적 ID로 주문 서비스와 재고 서비스의 기록을 잇는다.
- **health 확인 (health check)**: 서비스가 정상인지 묻는 HTTP 엔드포인트를 부르는 것이다. 이 저장소의 테스트 케이스에서 "정상"은 1초 안에 200으로 응답한다는 뜻이다.
